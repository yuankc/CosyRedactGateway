# 第二阶段：检测与摘要内核优化报告

本轮在已经完成请求限量、背压、取消、候选边界和并发控制的版本上继续优化。基线来自本轮修改前保存的 `.benchmarks/kernel-before/`，不是仓库最初版本，也没有用优化后代码重建旧基线。

结论：Node 环境的密集凭据样本取得约 5.7 倍的往返 P95 速度提升，128 KiB 代码样本耗时下降约 19%；峰值内存整体接近本轮基线。SSE 的测量结果存在时段差异，不能宣称稳定提速，更不能推断整个网关或模型调用提升 10 倍。

## 实际修改

- `worker.js`：使用 Aho-Corasick 多关键词自动机，替代每条规则分别执行 `includes`。只改变关键词预筛选，仍按原顺序执行正则、熵检查、白名单和候选预算；前后缀、重叠关键词以及无关键词规则均保留。自动机共享的只有固定规则结构，请求命中结果各自独立。
- `node-crypto.mjs`：使用 Node 内置 SHA-256，避免逐个提交 Web Crypto 摘要及逐字节转十六进制。每请求独立计数，首次及之后每 64 个新摘要让出事件循环；仍串行生成，保持错误顺序及映射语义。
- `node-server.mjs`：为每个请求注入独立的原生摘要函数。新模块用于隔离 Node 内置 API，保持 `worker.js` 的单文件 Web API 兼容性；没有新增第三方依赖。
- `scripts/benchmark.mjs`：默认测试 Node 摘要路径，可用 `--digest web` 检查 Web Crypto。报告明确标明当前、基线摘要实现，并记录摘要模块源文件哈希。
- 盐值、UTF-8 编码、SHA-256、占位符格式和检测规则均保持不变。未重写 JSON/SSE 处理，不引入跨请求敏感数据缓存。

## 定位依据

对固定 128 KiB 代码样本执行 150 次检测的 CPU 采样中，约 53.8% 的采样落在原有关键词 `includes` 回调。采样文件保存在 `.benchmarks/kernel-scan-before.cpuprofile`。这只是该样本的采样比例，不代表所有请求。
初步分段计时中，4000 个不同敏感值的扫描约 33–36 ms，原摘要路径约 263–330 ms，因此优先处理摘要调用成本。该实验仅用于定位；下面用完整请求测量评价最终收益。

## 完整请求性能

使用相同机器、Node 版本、固定种子和合成样本；模拟上游在内存中回显，不调用真实模型。每场景、每版本 5 个独立进程轮次，每轮先预热 20 批，再正式测量 100 批。下列 P95 是各轮 P95 的中位数，包含脱敏、模拟上游及恢复；CPU 还包含测试器工作，RSS 包含 Node、预生成样本和响应接收器。

| 场景 | 之前 P95 ms | 之后 P95 ms | P95 变化 | 之前 CPU ms/请求 | 之后 CPU ms/请求 | 之前峰值 RSS MiB | 之后峰值 RSS MiB |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 128 KiB 代码 | 31.48 | 25.54 | -18.87% | 29.22 | 22.81 | 132.77 | 136.24 |
| 4000 个不同邮箱 | 355.97 | 62.77 | -82.37% | 355.48 | 61.41 | 230.45 | 226.87 |
| 32 KiB Responses SSE（顺序测量） | 41.42 | 44 | 6.23% | 40.16 | 47.19 | 107.21 | 104.59 |
| 32 KiB Responses SSE（交替复测） | 41.72 | 39.19 | -6.06% | 42.97 | 40.94 | 107.03 | 105.27 |

| 场景 | 之前各轮 P95 范围 ms | 之后各轮 P95 范围 ms |
| --- | --- | --- |
| 128 KiB 代码 | 30.59～34.29 | 24.7～27.43 |
| 4000 个不同邮箱 | 337.82～412.45 | 62.33～88.44 |
| 32 KiB Responses SSE（顺序测量） | 37.61～41.95 | 42.92～53.21 |
| 32 KiB Responses SSE（交替复测） | 40.54～48.44 | 34.74～50.96 |

普通代码和密集凭据场景本次前后范围不重叠，观察到明确收益；范围不是统计置信区间，也不保证其他机器和生产负载得到相同比例。
SSE 顺序测量出现约 6.2% 的 P95 上升，因此追加了 AB、BA、AB、BA、AB 顺序的交替测量，每个 A/B 都是独立进程。交替结果中新版 3 组更快、2 组更慢，总体范围重叠；不能确认稳定提速或稳定回退。两组原始结果都保留，不能只引用较快的一组。
中间方案每次摘要都让出事件循环，密集场景峰值 RSS 约 346 MiB；最终改为每 64 次让出，回到约 227 MiB。该过程说明调度和分配也有成本，最终结果以当前表格为准。未通过生产环境强制 GC 或删除慢样本改善数据。

## 正确性与资源验证

- `npm test`：83/83 通过，包含现有真实 HTTP 背压、断开、超时、并发取消和流恢复测试。
- 新增关键词自动机等价性测试：500 组固定种子文本，与逐规则 `includes` 比对，覆盖重叠、重复、空关键词、Unicode 和 UTF-16 代理项。
- 单独对照本轮之前的完整检测器：500 组组合文本、5 种规则组合，分别使用正常和极小候选预算，共 1000 次比较；区间、规则、排序以及超限错误/计数一致。
- 验证 Node/Web Crypto 在不同盐值、中文、emoji、孤立代理项、重复值上的摘要和占位符完全一致，并验证嵌套 JSON、映射上限及碰撞拒绝。
- 新增批次取消测试：在第二个事件循环轮次取消，最多完成 64 个新摘要，取消后不继续写入映射。同步扫描和单次摘要本身仍不能被强制抢占。
- Node 和 Web Crypto 两条路径分别完成 14 场景快速对照，各 240 次正式请求，覆盖大文本、密集/重复凭据、嵌套 JSON、三种 SSE 协议及 4/8 并发；输入、脱敏输出、恢复输出摘要均一致。快速对照只验证行为，不据此判断速度。

## 验证边界

仅本机实现和验证，未部署远程服务。Node 摘要的收益不应直接套用到 Cloudflare/Deno；Web Crypto 路径是在 Node 中验证的，未实跑 Cloudflare/Deno。没有测量付费模型耗时、长时间生产内存积累或真实用户容量。本轮降低的是网关自身开销，不能按合成 RPS 推算可支持用户数量。
